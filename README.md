## 프로젝트 개요

암호화폐 선물 시장에서 **규칙 기반 매매 전략을 설계하고, 그 전략에 실제로 우위가
있는지 통계적으로 검증하는 것**이 목표다. 수익 자체보다 "이 전략이 우연이 아니라고
말할 수 있는가"를 판정하는 절차를 만드는 데 무게를 뒀다.

전략을 만드는 일보다 **자기 자신을 속이지 않는 일**이 어렵다. 과거 데이터로
파라미터를 고르면 무엇이든 좋아 보이고, 미래 정보가 한 칸만 새어 들어가도 결과가
완전히 뒤집힌다. 이 저장소의 상당 부분은 그걸 막는 장치다.

| | |
|---|---|
| **거래소** | Gate.io USDT 무기한 선물 |
| **종목** | BTC (추세 추종·회귀채널), XRP (차트 패턴 단타) |
| **검증 구간** | 2024-01-01 ~ 2026-07-31 (달력일 943일, 워밍업 뒤 271,553봉) |
| **상태** | 페이퍼 트레이딩 운용 중 (AWS Lightsail) |
| **테스트** | 511개 |

| F8 | 재시작 시 잔고와 보유 포지션을 복구한다 |

### 비기능 요구사항

| # | 요구사항 | 왜 |
|---|---|---|
| N1 | **미래 정보를 참조하지 않는다** | 한 칸만 새어도 백테스트가 무의미해진다. 실제로 5건의 시점 오류를 찾아 고쳤다 |
| N2 | **리플레이와 실시간이 같은 코드를 쓴다** | 별도 시뮬레이터를 뒀다가 체결 규칙이 어긋나 성과를 잘못 잰 적이 있다 |
| N3 | **수수료·슬리피지를 처음부터 포함한다** | 왕복 테이커 0.19%는 단타에서 승패를 가른다 |
| N4 | **파라미터는 한곳에 모은다** | 하드코딩된 숫자는 나중에 무엇을 왜 골랐는지 알 수 없게 만든다 |
| N5 | **비밀은 코드에 넣지 않는다** | 웹훅·API 키는 환경변수로만 읽는다 |
| N6 | **알림 실패가 매매를 막지 않는다** | 디스코드 장애로 봇이 멈추면 안 된다 |
| N7 | **리플레이가 실용 속도로 끝난다** | 지표를 봉마다 재계산하면 O(n²)가 되어 파라미터 탐색이 불가능해진다 |

reporting/    CSV/JSONL 로그, 디스코드 알림
tools/        수동 점검 스크립트 (실통신 확인, 과거 데이터 백필, 리플레이 CLI)
tests/        단위·회귀 테스트
deploy/       systemd 유닛 (봇 실행, S3 백업 타이머)

### 데이터 흐름

```
                    ┌──────────────┐
   Gate.io API ───► │ core/candles │ ── 결측·중복 검증
                    └──────┬───────┘
                           ▼
                    ┌──────────────┐
                    │  indicators  │ ── 전 구간 1회 계산 (Prepared)
                    └──────┬───────┘
                           ▼
                    ┌──────────────┐
                    │  strategies  │ ── Signal (진입가·손절힌트·목표힌트)
                    └──────┬───────┘
                           ▼
                    ┌──────────────┐
                    │     risk     │ ── 크기 산정 + 청산 계획, 상한 검사
                    └──────┬───────┘
                           ▼
                    ┌──────────────┐
                    │engine/broker │ ── 가상 체결
                    └──────┬───────┘
                           ▼
                       reporting
```

**실시간과 리플레이의 유일한 차이는 데이터 수집부다.** 리플레이는 `ReplayClient`가
캐시된 프레임을 돌려주고, 판단 시각만 옮기며 실제 `Engine.run_once(decision_ts=...)`를
호출한다. 진입 조건·리스크 판정·지정가 TTL·청산 규칙은 전부 같은 코드를 탄다.

### 두 개의 시계

봉 마감까지 기다리면 5분봉 기준 최대 5분간 손절이 방치된다. 코인에서 5분은
길다. 그래서 판단과 실행의 주기를 분리했다.

| | 주기 | 하는 일 | 입력 |
|---|---|---|---|
| **판단 시계** `run_once` | 봉 마감 | 지표, 국면, 패턴 판정, 신호 생성 | 확정봉만 |
| **실행 시계** `run_tick` | `poll_seconds` (10초) | 손절·익절·트레일 감시, 지정가 체결 | 진행 중인 봉 포함 |

**경계가 핵심이다.** 진행 중인 봉으로 지표를 계산하면 같은 시점을 다시 계산할
때 값이 달라져 검증 자체가 불가능해진다. 그래서 `core/live.py`는 실행 경로
전용이고, `indicators/`와 `strategies/`가 이걸 import하면
`tests/test_layering.py`가 실패한다.

#### 누적 고저를 그대로 쓰지 않는 이유

거래소가 주는 진행 중인 봉은 **누적** 고저다(봉 시작 이후 전체). 이걸 그대로
청산 판정에 넣으면 순서 정보를 잃어 없던 청산이 생긴다.

```
봉 시가 100 -> 99까지 눌림 -> 115까지 상승 (ATR 1.0)
  틱A: 저가 99 vs 손절 98 -> 통과. 트레일이 손절을 99로 올림
  틱B: 저가 99 vs 손절 99 -> 청산 98.98   ← 실제 가격은 114
```

99는 손절이 올라가기 *전에* 찍힌 값이라 체결될 수 없다. 그래서
`live.window_since()`가 직전 관측과 비교해 **그 사이에 실제로 지나온 구간**을
만들고, 그 구간으로만 판정한다. 회귀 테스트는
`test_exits_tick.py::test_지나간_저점으로_트레일_손절이_터지지_않는다`.

폴링 간격 때문에 봉의 마지막 몇 초는 어떤 틱도 보지 못한다. 봉이 넘어갈 때
`live.tail_window()`가 그 구간을 처리하고 `covered_bar_ts`를 올린다. 봉 시계는
이 값을 보고 이미 감시된 봉의 손절·익절을 다시 판정하지 않는다 — 다시 보면
위와 같은 이유로 잘못 청산된다.

틱 수집이 실패한 봉은 `covered_bar_ts`가 올라가지 않아 봉 시계가 평소처럼
전체를 판정한다. 안전한 쪽으로 무너진다.

### BTC

|---|---|
| `btc_regression_channel` | 1시간 100봉 회귀채널. 채널 반대편 이탈 후 채널선 2% 바깥에 지정가. 4시간봉 국면 역행 차단 |

### XRP — 고전 차트 패턴

패턴별로 잘 맞는 타임프레임이 달라 인스턴스마다 다른 봉을 쓴다.

| 패턴 | 타임프레임 | 확인 조건 |
|---|---|---|
| 컵앤핸들 | 5m / 15m / 1h / 4h | 손잡이 저점 후 컵 우측 고점 종가 돌파 |
| 이중천장·바닥 | 1h | 목선 **종가** 돌파 (두 번째 고점 진입 아님) |
| 쐐기 | 5m / 15m | 추세선 이탈 + 추세 일치 + 시간대 필터 |
| 헤드앤숄더 | 5m | 목선 종가 이탈 |
| 코테가와식 이격 | 1h | 급등락 후 평균 회귀 |
| 삼각수렴 | — | **비활성** (아래 참조) |

모든 패턴은 **"완성 확인 후 진입"** 원칙을 따른다. 패턴이 보이는 시점이 아니라
확정 신호(종가 돌파)가 나온 뒤 들어간다. 12개 항목의 품질 표를 만들어 4개 이상
충족해야 신호로 인정한다.

전략은 로그에 `strategy` 태그를 남겨 성과를 따로 집계한다. 합산하면 어떤 전략이
기여했는지 가려낼 수 없다.

## 설계 원칙

**1. 지표는 순수 함수로.**
입력은 DataFrame + 파라미터, 출력은 값. 전역 상태나 I/O를 넣지 않는다.
실시간 루프와 과거 검증에서 같은 함수를 재사용하기 위함이다.

**2. 미래 정보 참조 금지.**
피벗·VPVR·상위봉 국면처럼 확정 지연이 있는 계산은 `as_of` 위치 인덱스를 필수로
받는다. 다중 타임프레임 리플레이는 `시작 + 봉 길이`가 판단 시각을 지난 봉만
사용한다. 시장가 신호는 신호봉 종가가 아니라 **다음 봉 시가**에 체결해, 봉 마감 후
실제로 처음 주문할 수 있었던 가격을 쓴다.

**3. 레버리지는 결과값이다.**
손절 위치 → 손절 거리 → 포지션 크기 → 레버리지 순으로 계산한다. 청산가는 손절가보다
최소 3배 멀어야 한다. `btc_regime_25x`만 고정 레버리지 자체를 검증하는 별도
고위험 실험이라 잔고 10% 격리증거금과 25배를 명시적으로 덮어쓴다.

**4. 비용을 사이징에 포함한다.**
1% 리스크에 손절 가격차뿐 아니라 예상 진입·청산 수수료와 양방향 슬리피지를 처음부터
넣는다. 손절 거리 하한도 왕복 테이커 비용의 2배(≈0.38%)로 **수수료에서 유도한다.**
이보다 좁으면 이겨도 수수료가 수익의 절반을 가져간다.

**5. 진입하지 않은 신호도 기록한다.**
리스크 상한이나 필터에 걸려 스킵된 신호도 남긴다. "막았던 신호가 실은 더 좋았는지"를
나중에 판단하기 위해서다.

**6. 롱/숏은 따로 집계한다.**
크립토는 상승 편향이 있어 같은 규칙이라도 방향별 통계가 다르다. 합쳐 보면 한쪽이
다른 쪽을 가린다. 실제로 `btc_regime_25x`는 필터 전 롱 +155 / 숏 −532로,
합계만 봤다면 원인을 못 찾았다.

**7. 알림 실패가 매매를 막지 않는다.**
디스코드 웹훅은 try/except로 감싸고, 실패해도 루프는 계속 돈다.

## 검증 방법론

이 프로젝트에서 가장 공을 들인 부분이다. 아래는 설계 원칙의 요약이며, 숫자의 정확한
집계 단위와 비용·체결 가정은 [MEASUREMENTS.md](MEASUREMENTS.md)를 따른다. 전략 변경의
가설과 채택 여부는 [EXPERIMENTS.md](EXPERIMENTS.md)에 기록한다.

### 앞뒤 절반 분할 검증

**표본을 시간순 절반으로 나눠 양쪽 모두 플러스일 때만 필터를 채택한다.**
한쪽만 좋으면 과적합으로 본다.

이 규칙 덕분에 여러 번 "좋아 보이는" 아이디어를 버렸다. 예를 들어 삼각수렴 전략은
진입 방식·목표·보유시간·시간대·변동성·MA 정렬·MACD·RSI·VWAP·RVOL 등 약 20개 축을
탐색했지만 **어느 조합도 양쪽 절반이 함께 플러스가 아니었다.** 앞 절반 마이너스 /
뒤 절반 플러스가 반복됐고, 결국 비활성화했다.

반대로 채택한 예 — `btc_regime_25x`의 회귀 결정계수 임계값:

```
R²    건수   승률      손익      앞절반    뒤절반
0.55   675  52.7%    -88.4    -279.2   +190.8
0.62   598  53.0%    -16.3    -151.3   +135.0
0.64   569  54.1%   +297.9     +28.0   +270.0  ✓
0.68   503  54.9%   +475.6    +248.1   +227.5  ✓  ← 채택
0.74   414  55.6%   +544.7    +469.7    +75.0  ✓
0.78   333  53.8%    +96.1    +153.0    -56.8
```

0.64~0.76이 전부 양쪽 플러스인 **고원**이라 단일 스파이크가 아니다. 최고점(0.74)이
아니라 고원 중앙을 골랐다 — 최고점 고르기는 과적합이다.

### 미래참조 방지

시점 오류는 조용히 지나가고 결과만 좋게 만든다. 실제로 찾아 고친 것들:

- 지정가 주문이 **주문 이전 가격**에 체결되던 문제
- 같은 봉이 두 번 평가되던 문제
- 상위봉 국면을 **진행 중인 봉**으로 판정하던 문제 (전체 봉의 12.3%에서 라벨이 갈렸다)
- 포지션 보유 시간이 자기 타임프레임이 아닌 5분봉 기준으로 세어지던 문제

마지막 것 때문에 1시간봉 포지션이 3.3시간 만에 40봉 시간 손절에 걸렸고,
`double_top.1h`의 청산 50건 중 47건이 시간 손절이었다.

### 변이 테스트

회귀 테스트가 정말로 그 버그를 잡는지 확인한다. 고친 코드를 일부러 다시 망가뜨려
테스트가 실패하는지 본다.

이 과정에서 **내 테스트가 실은 버그를 못 잡는다는 걸 두 번 발견했다.** 한 번은 호출
순서가 문제를 가리고 있었고(테스트를 다시 썼다), 한 번은 바이트 길이가 같아 파이썬이
`__pycache__`를 재컴파일하지 않아 변이 테스트 자체가 무효였다.

### 데이터 정합성

Gate 공식 아카이브의 컬럼 순서는 `ts,volume,close,high,low,open`으로 **OHLC가
아니다.** 이걸 OHLC로 읽으면 96%의 봉에서 시가와 종가가 뒤바뀌는데, 검증 함수는
그대로 통과한다. 봉의 방향에 의존하는 패턴 인식이 전부 조용히 망가진다.
서로 다른 네 값을 쓰는 회귀 테스트로 고정했다.

### 장기 리플레이를 기대수익으로 읽으면 안 되는 이유

포트폴리오로 읽으실 분을 위해 명시한다. **이 수치는 실제 기대 수익률이 아니다.**

1. **인샘플 오염** — 타임프레임 선택, 시간대 필터, R² 임계값, 삼각수렴 비활성화가
   전부 *이 943일을 보면서* 정해졌다. 진짜 아웃오브샘플은 전략 버전을 먼저 고정한
   뒤의 독립 기간이어야 한다.
2. **체결 가정** — 지정가는 가격이 닿으면 체결된다고 본다. 실제로는 호가 대기열이
   있어 닿아도 체결되지 않을 수 있다.
3. **슬리피지 고정** — 0.02% 일괄 적용. 실제로는 변동성과 규모에 따라 달라진다.
4. **부분 체결 없음** — 전량 체결만 모델링한다.
5. **표본 부족** — `cup_handle`은 943일에 1~2건이다. 통계적 의미가 없다.

## CI/CD

### CI — GitHub Actions

[`.github/workflows/ci.yml`](.github/workflows/ci.yml)

```yaml
on:
  push:        { branches: [main] }
  pull_request: { branches: [main] }
```

| 항목 | 설정 | 이유 |
|---|---|---|
| 트리거 | push + pull_request | PR에서 돌아야 **머지 전에** 걸러진다 |
| `concurrency` | 이전 실행 취소 | 연속 푸시 시 최신 결과만 의미가 있다 |
| `permissions` | `contents: read` | 토큰 권한 최소화 |
| `timeout-minutes` | 10 | 기본값 360분이라 멈추면 무료 시간을 다 먹는다 |
| 캐시 | pip | matplotlib·pandas·numpy 설치가 무겁다 |

실행 시간 약 40초, 테스트 511개.

**의도적인 설계 하나** — `data/`는 `.gitignore` 대상이라 CI 체크아웃에는 캔들 캐시가
없다. 테스트가 캐시나 실제 거래소 API에 의존하면 CI에서 깨진다. 이건 버그가 아니라
**감지 장치**다. 거래소 호출은 전부 `httpx.MockTransport`로 막혀 있어야 한다.

### CD — 미구축

현재 배포는 rsync 수동 방식이다. 다음 순서로 개선 예정이며, 핵심 목표는 자동화
자체가 아니라 **배포 추적성**이다.

- [ ] 커밋 기반 배포 (실행 중인 코드 = 특정 커밋으로 확정)
- [ ] 테스트 통과 시에만 재시작, 실패 시 이전 커밋 자동 복구
- [ ] 배포 커밋 해시를 디스코드로 알림
- [ ] 포지션 보유 중 재시작 처리

> 라이브 성과를 해석하려면 "언제 무엇이 바뀌었는지"를 알아야 한다. rsync는 커밋하지
> 않은 로컬 수정까지 밀기 때문에 서버 코드가 어느 커밋과도 일치하지 않을 수 있다.
> 매매봇에서는 이게 자동화보다 중요한 문제다.

`data/trades.csv`·`data/signals.jsonl`·`data/state.json`과 혼동하지 않는다.

#### 실행 시계 검증

봉 경로와 틱 경로를 같은 구간에서 돌려 비교한다. **성과가 좋아지는지를 보는
도구가 아니라, 두 경로가 설명 가능한 방향으로만 갈리는지 보는 도구다.**

```bash
./.venv/bin/python -m tools.compare_tick --last 1700           # 봉 vs 틱
./.venv/bin/python -m tools.compare_tick --last 1700 --maker   # 틱 vs 틱+메이커
```

한 번에 변수 하나만 바꾼다. 틱 시계와 메이커 전환을 동시에 켜면 진입 시점이
달라져 두 실행이 아예 다른 거래를 하게 되고, 어느 쪽 변경의 효과인지 구분할 수
없다. 진입이 갈라지면 도구가 지연 비교를 생략한다.

틱 재생은 1분봉을 틱 대용으로 쓴다. **거래소가 1분봉을 약 6일치만 주므로
`--last`로 최근 구간만 돌려야 한다.** 구간이 안 덮이면 에러로 죽는다 — 조용히
봉 모드로 떨어지면 "틱으로 검증했다"는 잘못된 결론이 남기 때문이다.

리플레이 시간이 봉 경로의 20배 이상이다(봉마다 틱 5회 × 수집·ATR).
검증용으로만 쓴다.

### 실시간 (페이퍼)

```bash
cp .env.example .env     # 디스코드 웹훅 URL 입력
chmod 600 .env
./.venv/bin/python -m engine.loop
```

### 데이터 제약

Gate.io REST API는 타임프레임당 **최근 10,000봉까지만** 준다. 초과 요청은
400(`Candlestick too long ago`). REST만 썼을 때의 최대 깊이:

| | 봉 수 | 기간 |
|---|---:|---|
| BTC 1d | 800 | 799일 |
| BTC 1h | 9,600 | 400일 |
| XRP 5m | 9,216 | **32일** |

XRP 5분봉 32일로는 패턴 검증이 불가능하다. Gate 공식 월별 아카이브
(`download.gatedata.org`)로 달력일 943일까지 보강한다. 아카이브는 완결된 달, REST는 현재
달과 중복 구간을 담당하며 중복 시 REST를 우선한다. 아카이브가 제공하는 간격은
`1m/5m/1h/4h/1d`뿐이라 15분봉은 5분봉에서 합성한다.

## 운영 · 데이터 백업

소스코드는 Git으로, 실행 데이터는 비공개 S3 버킷에 별도 백업한다. **S3는 실행
저장소가 아니다.** 봇은 항상 Lightsail 로컬 `data/`를 사용하므로 S3 장애나 백업
실패가 매매 루프에 영향을 주지 않는다.

| 대상 | 주기 | S3 경로 |
|---|---:|---|
| `state.json`, `trades.csv`, `signals.jsonl` | 매일 | `runtime/daily/YYYY-MM-DD/` |
| `data/cache/` 과거 캔들 | 매주 | `market-data/current/` |

OI(`*_oi.csv`)는 최초 스냅샷만 보관하고 주간 동기화에서 제외한다. 실시간 서버와
장기 원본의 수집 범위가 달라, 짧은 서버 파일이 장기 원본을 덮어쓰는 것을 막기
위해서다.

서버 설정은 `/etc/xrp-paper-bot/backup.env`에 두고 Git에 넣지 않는다.

```bash
BACKUP_BUCKET=xrp-paper-bot-backup-ACCOUNT-apne2
AWS_REGION=ap-northeast-2
AWS_PROFILE=xrp-paper-bot-backup
BOT_ROOT=/home/ubuntu/xrp-paper-bot/v2
```

수동 확인:

```bash
sudo systemctl start xrp-paper-bot-backup-runtime.service
sudo systemctl start xrp-paper-bot-backup-market.service
sudo systemctl list-timers 'xrp-paper-bot-backup-*'
```

복원할 때는 먼저 봇을 멈추고 대상 날짜를 명시한다. `state.json`만 복원하면 체결
로그와 시점이 어긋날 수 있으므로 같은 날짜의 세 파일을 함께 확인한다. 실거래 전환
후에는 로컬 상태가 아니라 **거래소의 실제 포지션**을 원본으로 삼아 반드시
재조정(reconciliation)해야 한다.

## 알려진 한계

### 전략

- 기존 장기 리플레이 스냅샷에서 `head_shoulders.5m`이 64건 −109.84로 유일한 손실
  전략이다. 추세 필터를 넣었지만 아직 해결되지 않았다
- `cup_handle`은 15m/1h/4h에서 943일 동안 1~2건뿐이라 판단할 표본이 없다.
  실시간으로 모으는 중이다
- `btc_regression_channel`의 지정가 만료율이 75%다 (216건 제출 → 163건 만료).
  진입 이격이 넓을 가능성이 있다
- 삼각수렴은 약 20개 축을 탐색했으나 앞뒤 절반이 함께 플러스인 조합이 없어
  비활성화했다. 코드와 테스트는 남겨뒀다 — `kotegawa`는 180일 표본에서 −60%였다가
  943일에서 +459로 뒤집힌 전례가 있다

### 구현

- 격리마진 예약과 강제청산을 실제로 구현하지 않았다. `btc_regime_25x`의 25배는
  수량 계산에만 반영된다
- 동시 리스크는 실측 상관 모형이 없어 방향과 무관하게 100% 합산한다
- 지정가 체결에 호가 대기열 모델이 없다
- `LEVERAGE_CAP`은 실제로 발동한 적이 없다 (필요 레버리지 최대 약 1.75배).
  현재는 휴면 안전장치이며, 과도한 레버리지는 `RISK_MULTIPLIER`로 제어한다
